# HU-01: Registro de nodo institucional (IES)

## Qué se hizo y por qué
Una universidad envía NIT, nombre, dominio web y correo de contacto. El sistema crea el nodo con estado `PENDIENTE_APROBACION` y un identificador `node_id` (`IES-XXXXXXXX`). Aún no tiene API Key: eso es HU-02. Un NIT repetido se rechaza para evitar solicitudes duplicadas. El endpoint es público, porque quien se registra todavía no tiene credenciales.

## Archivos
- Nuevos: `src/app/{config,models,repositories,main}.py`, `src/app/routers/nodes.py`, `tests/test_hu01_register_node.py`, `thunder-tests/` (carpeta "App final").
- Repositorio: una interfaz con implementación en memoria (por defecto) y DynamoDB (`REPOSITORY_BACKEND=dynamodb`).

## Cómo ejecutarlo
```bash
uvicorn src.app.main:app --reload --port 8001
curl -i -X POST http://127.0.0.1:8001/api/v1/nodes/register -H "Content-Type: application/json" \
  -d '{"nit":"899999063-3","name":"Universidad Nacional de Colombia","domain":"unal.edu.co","contact_email":"admisiones@unal.edu.co"}'
pytest tests/test_hu01_register_node.py
```
Respuesta esperada: `201` con `{"node_id":"IES-...","status":"PENDIENTE_APROBACION",...}`. Repetir el envío da `409`.
Las pruebas oficiales las corre el CI de GitHub.

## Criterios de aceptación
- [x] GIVEN el formulario `/registro-nodo` (aquí: `POST /api/v1/nodes/register`), WHEN envía NIT, nombre, dominio y correo, THEN el nodo queda en `PENDIENTE_APROBACION` y se genera un ID. Cubierto por `test_registro_valido_crea_nodo_pendiente`.
- [x] Errores: campos faltantes o inválidos (422), NIT duplicado (409).
- [x] Persistencia en DynamoDB probada con `moto`.

## Decisiones
- HU-01 expone solo la API. El "formulario" web queda para la fase de frontend (BRECHAS B10).
- Unicidad por NIT con `Scan` en DynamoDB: el catálogo es pequeño y evita crear un índice. Se revisa si crece.
- Dominio y correo se guardan en minúsculas.
- Sin protección anti-spam (rate limit) por ahora; el API Gateway limita la tasa en AWS.
